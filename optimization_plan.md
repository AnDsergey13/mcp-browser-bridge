## 1. Правила безопасности правок (репозиторий рабочий)

Эти механизмы НЕ отключать и НЕ ослаблять ни в одном пункте плана:

- **Policy-конвейер** в `mcp.ts callTool`: шаги 1–7 (session state → паузы →
  STATE_DIVERGED → policy.check → consent → pacing). Любой новый инструмент
  проходит через тот же конвейер; новые page-инструменты добавлять в
  `PAGE_TOOLS` (capability `read`), новые act-инструменты — в `ACT_TOOLS`
  (capability `interact` + pacing).
- **Конверт ответа** `{ok, data|error_code, hint, policy_reminder}` — структуру
  не менять. Разрешено: делать `policy_reminder` условным (П0-1) — поле
  остаётся, содержимое сокращается.
- **Pacing** (`pacing.ts`, 0.4–2.5 c, окно 30 act/мин), **consent-флоу**,
  **авто-паузу**, **capResponse** (модифицировать — да, удалять — нет).
- **Gating не обходить никогда** (AGENTS.md): ни один пункт плана не должен
  давать обход `ACTION_DENIED / CAPABILITY_DENIED / DOMAIN_NOT_ALLOWED`.
- **После каждого этапа**: `npm test` в `bridge-server/` (18/18: mcp-smoke,
  policy, relay, file-repl) + `scripts/live-check.mjs`. Каждый этап —
  отдельный коммит (в репо есть skill git-commit-writer).
- **Поверхность инструментов контролируется тестом**: добавление инструмента =
  правка `mcp-smoke.test.mjs` (16→17→18) + `PROTOCOL.md` + `AGENTS.md` в том же
  коммите. Это осознанный gate, не обходить.

## 2. Этап P0 — дешёвые правки, мгновенная экономия (каждая 1–3 часа)

### П0-1. `policy_reminder` по версии, а не в каждом ответе
**Файлы**: `mcp.ts` (`callTool`, `finish`, `reminder()`), `memory.ts`
(`buildPolicyReminder`).
**Что**: сервер считает хэш содержимого reminder (пресет+домен+тексты плейбуков).
Полный reminder отдаётся: (а) при первом вызове сессии, (б) при смене хэша,
(в) раз в 10 вызовов. Иначе — короткая форма `{preset, domain, reminder_version}`.
**Нюансы**:
- Ошибки gating (`ACTION_DENIED`, `CAPABILITY_DENIED`, `AUTO_PAUSED_HUMAN_NEEDED`,
  `STATE_DIVERGED`) — ВСЕГДА с полным reminder: там он несёт смысл для модели.
- Версия должна меняться при hot-reload policy.yaml (fs.watch в `policy.ts`) и
  при записи плейбука — хэш содержимого покрывает оба случая автоматически.
- НЕ трогать `memory.journal` — он пишет digest и нужен для аудита.

### П0-2. Компактный JSON
**Файл**: `mcp.ts` (строка с `JSON.stringify(payload, null, 2)`).
**Что**: `JSON.stringify(payload)` без indent.
**Нюансы**:
- Формат снапшота — построчный текст внутри JSON, читаемость не пострадает.
  Логи сервера не затронуты (они отдельные).
- Файл-REPL (`index.ts startFileRepl`) пишет result.json СВОИМ
  `JSON.stringify(payload, null, 2)` — это отдельный канал для скриптов,
  токенов модели не потребляет; можно оставить pretty (удобно для отладки)
  или унифицировать — на расход не влияет.

### П0-3. `{unchanged:true}` по dom_hash в page.snapshot
**Файл**: `mcp.ts` (execute `page.snapshot`, кэш `this.snapshots`).
**Что**: если свежий `dom_hash` совпал с кэшированным — ответ
`{unchanged:true, dom_hash, url}` вместо полного текста.
**Нюансы** (критично):
- Ключ кэша обязан включать `tabId + scope + selector`. Сейчас кэш
  `Map<tabId, CachedSnapshot>` — снапшот с `scope:"full"` после `scope:"viewport"`
  при совпадающем dom_hash даст ложный unchanged. Расширить ключ или хранить
  параметры в записи и сравнивать.
- При `unchanged:true` refs остаются валидными из серверного кэша —
  `parseSnapshotRefs` заново не нужен, но и кэш НЕ затирать.
- line-diff НЕ делать на этом этапе (отдельная задача, риск рассинхрона).

### П0-4. Убрать `debug_settle` из ответа act.type
**Файл**: `content-bridge.js` (`handlers.type`, ~стр. 3060–3068).
**Что**: поле `debug_settle` не включать в ответ; писать в серверный лог через
evt (или выкинуть совсем).
**Нюанс**: у `pressKey` debug-поля нет — только settle-задержка; его не трогать.

### П0-5. Скриншот: даунскейл + защита от резака
**Файлы**: `background.js` (`screenshotCommand`, TODO(MVP) даунскейл),
`compress.ts` (`capResponse`).
**Что**: (а) реализовать даунскейл ≤1280px/q70 (canvas в background page —
MV2 persistent, canvas доступен); (б) в `capResponse` исключить поле
`data_jpeg_base64` из обрезки — лучше вернуть ошибку `SCREENSHOT_TOO_LARGE`,
чем обрубок base64.
**Нюанс**: описание инструмента уже обещает «≤1280px, q70» — код ему не
соответствует; после правки описание станет честным. MCP image content не
вводить на этом этапе (смена контракта ответа — отдельное решение).

### П0-6. Таймаут file.download на больших файлах (дубликаты при ретрае)
Зафиксировано пользователем в backlog (коммит `82c04cf4`): zip 283 МБ
релеется дольше 30-секундного MCP-таймаута → клиент видит
`MCP error -32001: Request timed out`, трансфер доживает в фоне, ретрай
создаёт `name (1).zip`.
**Что (минимум, дёшево)**:
(а) Правило уже в AGENTS.md — дополнить описание инструмента `file.download`
в `defs` фразой «при таймауте -32001 НЕ повторять вызов: проверить
`downloads/manifest.jsonl` (status ok), трансфер может завершиться в фоне».
ВАЖНО: hint в ответе/ошибке бесполезен — `-32001` это КЛИЕНТСКИЙ таймаут
MCP-SDK, ответ сервера клиент не дождётся; единственные места, где модель
это увидит заранее, — описание инструмента и AGENTS.md.
(б) Идемпотентность на сервере (`downloads.ts`): если в manifest.jsonl есть
завершённая запись с тем же `url`+`name` (и размер/sha256 совпадают с
только что скачанным) — вернуть существующий файл вместо повторной передачи.
**Что (правильное лечение, если минимума мало)**: MCP progress-нотификации
во время релея (SDK сбрасывает таймаут по progress) — отдельная задача,
проверить поддержку в используемой версии `@modelcontextprotocol/sdk`.
**НЕ делать**: «чинить» per-chunk ack релея или поднимать лимиты — релей
рабочий (80 МБ проходят), проблема только в таймауте ожидания ответа.
Правило «большие файлы — через скрипты файл-REPL» уже задокументировано
пользователем и остаётся в силе.

## 3. Этап P1 — убираем reasoning-петли (каждый пункт 0.5–2 дня)

### П1-1. `page.wait_for` — событийное ожидание условия (17-й инструмент)
**Файлы**: `mcp.ts` (PAGE_TOOLS, defs, execute), `content-bridge.js` (новый
handler на MutationObserver), `PROTOCOL.md`, `AGENTS.md`, smoke-тест (16→17).
**Что**: `{tabId, condition:{text?:string, ref?:string, url_contains?:string},
state?:"appear"|"disappear"|"stale", timeout_ms?:≤30000}`. Реализация на
существующем MutationObserver в content script; ответ первым событием, без
polling снапшотами.
**Нюансы**:
- Это ГЛАВНАЯ замена самой дорогой петли «модель поллит page.snapshot».
- Таймаут — не ошибка gating: `{ok:true, data:{condition_met:false}}`, чтобы
  модель планировала дальше, а не упиралась в error.
- Ограничить один активный wait на вкладку (очередей в протоколе нет — осознанно).

### П1-2. `act.batch` — пакет действий (18-й инструмент)
**Файлы**: `mcp.ts`, `content-bridge.js`, тесты, `PROTOCOL.md`.
**Что**: `{tabId, steps:[{do:"click"|"type"|"select"|"key", ref|text, ...}]}`
→ один ответ с одним after-блоком.
**Обязательные ограничения** (зафиксировано ревью):
- Каждый элемент пакета проходит `policy.check()` ПОШТУЧНО до начала выполнения
  (все проверки — атомарно в начале; gated-действие без гранта = весь пакет
  отклонён, partial execution недопустим для gated).
- Каждое действие учитывается в скользящем окне 30 act/мин; между шагами —
  уменьшенный jitter (например 0.3–0.8 c), НЕ нулевой: human-like модель pacing
  сохраняется.
- Максимум 10 шагов за вызов.

### П1-3. Авто-retry после STALE_REF
**Файл**: `mcp.ts` (`callTool`, кэш `snapshots[tabId].refs`).
**Что**: при `STALE_REF` на act.* сервер один раз: переснимает снапшот → ищет
элемент по сохранённому `text` из кэша refs → повторяет действие → в ответе
помечает `{retried:true, new_ref}`.
**Нюансы**:
- Ровно ОДИН retry, без рекурсии.
- Если действие gated — новый ref проходит `classifyElement` заново; категория
  изменилась → честный отказ, а не выполнение.
- Если поиск по тексту даёт >1 кандидата — НЕ выбирать молча: вернуть STALE_REF
  с кандидатами (как AMBIGUOUS в click-by-text).

### П1-4. Div-суп: дедуп pointer-цепочек + чистый скоуп
**Файл**: `snapshot.js` (`isInteractiveEl`, `build`, `labelOf`).
**Что**:
(а) Если у элемента с `cursor:pointer` есть предок с `cursor:pointer` и тем же
innerText — оставлять только нижний (deepest meaningful): он ближе к тексту,
клик по нему надёжнее.
(б) Исключить `header, nav, footer, aside` из интерактивного обхода `build()`
при дефолтном скоупе (сейчас они исключены только из `compressedText`).
**Нюансы**:
- `scope:"full"` и явный `selector` — старое поведение сохранить (модель может
  осознанно хотеть меню).
- На сайтах без `<main>` скоуп = body: проверить на живом кейсе, что меню не
  нужно для навигации по SPA; если нужно — вместо исключения опускать такие
  элементы В КОНЕЦ снапшота.
- Заодно: `refs.assign` — O(n²) дедуп проходом по map; заменить на
  `WeakMap<Element, ref>` (поведение не меняется, 300 элементов — ощутимо).

### П1-5. Структурная дедупликация повторов
**Файл**: `snapshot.js` (`describe`, `build`).
**Что**: ≥5 подряд идущих строк с одинаковой сигнатурой (role + одинаковый
текст-шаблон, напр. 50 кнопок «Купить») сворачиваются:
`[e12..e61] button "Купить" ×50`.
**Нюанс**: диапазон `e12..e61` должен оставаться адресуемым — refs выданы всем
элементам, свёртка только визуальная. `act.click` по любому ref из диапазона
обязан работать.

## 4. Этап P2 — структурные улучшения (итерация)

### П2-1. Div-суп в extractMarkdown — СВОИМИ эвристиками, БЕЗ внешних библиотек
**Файл**: `snapshot.js` (`extractMarkdown`, `walkMd`).
**ОГРАНИЧЕНИЕ ПОЛЬЗОВАТЕЛЯ (коммит 6ebdf51c, 2026-08-15):** «собственный
обходчик DOM → чистый markdown (без внешних зависимостей; Readability не
используем)». Встраивать Readability/Defuddle ЗАПРЕЩЕНО — решение принято
осознанно (ноль зависимостей в content script). Вместо библиотеки переносим
её ИДЕИ в свой код:
**Что**: детектор div-супа: если в `src` мало `<p>/<h*>/<li>` при большом
textContent (например p+h+li < 10 и текст > 2000 симв.) — walkMd переключается
в density-режим: скоринг блоков по text-density (длина текста узла / длина
текста поддерева) и link-density (доля текста внутри `<a>` — у меню она
высокая, у контента низкая), склейка соседних текстовых div/span в абзацы,
отсечение блоков-«хвостов» (футеры, related-ссылки) по link-density > 0.5.
Это 30–60 строк своего кода, без зависимостей.
**Нюансы** (неочевидные связки с кодом пользователя):
- НЕ ломать контракт с `localize-page.py`: маркеры `[embedded: url]`,
  `[video: url]`, `![alt](src)` и манифест `images` обязаны сохраняться и в
  density-режиме (density-скоринг применяется к текстовым блокам; медиа-узлы
  обрабатываются как сейчас, до скоринга).
- Индексная синхронизация `data-bridge-visible` (img[i] оригинала ↔ img[i]
  клона) хрупка: любая перестройка обхода в этом пункте обязана перевести
  маркировку на установку атрибута НА ОРИГИНАЛЕ до клонирования (клон
  унаследует атрибут — индексы не нужны).
- `extractMarkdown` не имеет своего лимита — добавить `max_chars` (например
  15000) ДО серверного capResponse: резка по границе абзаца лучше, чем
  обрубок строки резаком.
- **Критерий отката**: если density-режим на 2–3 реальных div-суп-сайтах даёт
  мусор (теряется основной текст) — НЕ дотягивать эвристики молча, а доложить
  пользователю: решение «без внешних зависимостей» его, пересмотр — тоже его.

### П2-2. Параметр `images` в page.extract (обратная совместимость!)
**Файлы**: `mcp.ts`, `snapshot.js`.
**Что**: `images?: "inline"|"manifest"|"off"`, дефолт `"inline"`.
**Нюанс — КРИТИЧНО**: `localize-page.py` вызывает `page.extract` БЕЗ параметров
и ждёт `images` со `src` + инлайн-URL в markdown. Дефолт обязан остаться
текущим поведением, иначе скрипт пользователя сломается. `"off"` — для задач
чистого чтения (экономия до нескольких KB на странице с src ≤1000 симв. каждый).
Заодно: `clean(srcUrl, 1000)` — 1000 символов на URL это много; CDN-URL с
подписями реально длинные, но для модели хватает 300 — согласовать с
`localize-page.py` (он берёт src из манифеста, не из markdown).

### П2-3. `page.scan` — автоскролл ленты с агрегацией (19-й инструмент)
**Что**: auto-scroll до стабилизации числа интерактивных (3 итерации без роста)
или лимита экранов; агрегация уникальных строк с дедупом по сигнатуре.
**Нюанс**: стоп-условие обязательно — «бесконечные» ленты; жёсткий лимит
(например 20 экранов / 60 c). Pacing на scroll применять как к act.*.

### П2-4. Метрики и плейбуки
**Файлы**: `memory.ts` (journal), опционально `scripts/`.
**Что**: (а) агрегатор расхода: journal уже пишет `bytes` в digest — скрипт
`scripts/token-stats.py` (суммы по инструментам за сессию; это ЕДИНСТВЕННЫЙ
способ проверить, что П0-П2 реально сэкономили); (б) опция журналировать
полные args (флаг в policy.yaml, default off) → экспорт «успешная цепочка →
черновик плейбука» в `memory/domains/<domain>.md`.
**Нюанс**: полные args могут содержать вводимый текст (пароли нельзя — тип
password уже gated, но всё равно: маскировать значения `act.type` в полях
login-форм при журналировании args).

### П2-5. (Опционально, из backlog пользователя) In-page баннер download-гранта
**Что**: при `CAPABILITY_DENIED` на `file.download` сервер включает домен файла
в ошибку; расширение показывает на странице баннер «нужен доступ к домену X»
с выдачей гранта на месте (consent-механика, `grant.add` из content script).
**Нюансы**:
- Новый evt/командa в протоколе — правка `PROTOCOL.md` обязательна.
- Default-deny не ослабляется: баннер только ПРЕДЛАГАЕТ, решение — пользователь.
- Не путать с consent-баннером gated-категорий: другой поток (домен файла ≠
  домен вкладки), отдельный текст, чтобы пользователь понимал, ЧЬЮ загрузку
  разрешает.

### П2-6. (Опционально, из backlog коммита 6ebdf51c) Авто-переинжекция content scripts
**Что**: после reload расширения открытые вкладки продолжают выполнять СТАРЫЕ
content scripts (нужен F5, задокументировано в SETUP.md). Реализовать
переинжекцию в открытые вкладки грантованных доменов из `background.js` при
старте расширения (`tabs.query` + `tabs.executeScript` по match_patterns
политики).
**Нюансы**:
- Инжектить ТОЛЬКО в домены с активными грантами (policy на сервере — список
  получить от сервера или из storage расширения), не во все вкладки подряд.
- После переинжекции ref-реестр вкладки пуст → серверный кэш снапшота для
  вкладки инвалидировать (событие на сервер или смена dom_hash при следующем
  snapshot — второе проще и уже работает).
- Пункт не про токены, а про эксплуатационную надёжность; можно отложить без
  влияния на остальной план.

## 5. Ловушки и неочевидные взаимосвязи (прочитать ДО начала работы)

1. **Файловый REPL встроен в MCP-сервер, но слот по-прежнему один**
   (коммит `82c04cf4`). `hls-download.py` / `localize-page.py` /
   `bridge-call.sh` пишут в `/workspace/.bridge/cmd.json`, сервер забирает
   команду poll'ом каждые 700 мс. Два скрипта параллельно = гонка и
   потерянные команды — план НЕ добавляет параллелизма в этот канал.
   Новые следствия встройки REPL в серверный процесс:
   - скрипты и модель делят ОДИН `core.callTool`: act.* из скриптов едят
     то же pacing-окно 30 act/мин, что и действия модели — при П1-2
     (act.batch) это учесть в документации;
   - серверный кэш снапшотов общий: пересъём снапшота скриптом влияет на
     `{unchanged:true}` модели (П0-3) — это корректно (кэш всегда свежий),
     но при отладке «почему unchanged» помнить, что снапшот мог сделать
     скрипт;
   - REPL исполняет любой инструмент без MCP-клиента: канал защищён только
     тем, что писать в `/workspace/.bridge/` может лишь процесс в контейнере;
     policy-конвейер при этом полный (callTool), default-deny не обходится.
2. **Кольцевой буфер net.list = 50.** При долгом просмотре старые m3u8
   вытесняются. `hls-download.py --net` должен запускаться сразу после старта
   воспроизведения — это процедурное ограничение, зафиксировать в AGENTS.md,
   а не «чинить» увеличением буфера (память вкладки).
3. **net.list слушает `["media","xmlhttprequest"]`.** HLS через hls.js — это
   XHR/fetch, ловится regex'ом по URL; потоки, отдаваемые как `fetch` без
   расширения в URL (signed endpoints), не поймаются — известное ограничение,
   документировать, не расширять на все типы запросов (шум).
4. **После П0-2 (компактный JSON)** все снапшоты станут однострочными JSON —
   `parseSnapshotRefs` в `classifier.ts` парсит СТРОКИ снапшота регулярками;
   проверить, что он работает от `text` внутри data, а не от pretty-print
   форматирования (в коде — от строки снапшота, регрессии быть не должно, но
   прогнать relay-тест обязательно).
5. **П0-3 + П1-3 взаимодействие**: авто-retry переснимает снапшот — этот
   пересъём ОБЯЗАН обновлять кэш `snapshots[tabId]`, иначе следующий
   page.snapshot даст ложный `unchanged:true` против протухшего кэша.
6. **hls-download.py качает каждый сегмент отдельным `file.download`** через
   браузер с per-chunk ack — медленно на 500-сегментных потоках, но токенов
   не потребляет (идёт мимо модели). НЕ оптимизировать в рамках этого плана:
   это не токен-проблема, а риск сломать работающий релей.
7. **Smoke-тест «ровно N инструментов»** — сознательный gate поверхности MCP:
   каждый новый инструмент правит тест + PROTOCOL.md + AGENTS.md одним
   коммитом. Не «чинить» тест ослаблением assert'а.
8. **Описание `page.screenshot` уже врёт** («≤1280px, q70» — не реализовано):
   П0-5 это исправляет; до него описание не использовать как документацию.
9. **Внешние библиотеки в content script ЗАПРЕЩЕНЫ** (коммит 6ebdf51c:
   «без внешних зависимостей; Readability не используем»). Все улучшения
   `snapshot.js`/`extractMarkdown` — только свой код. Маркировка
   `data-bridge-visible` по индексу `img[i]` хрупка — при переработке
   walkMd (П2-1) перейти на маркировку оригинала до клонирования.
10. **Нет egress у контейнера — окончательно** (прокси → 403, выяснено
    2026-08-15): никаких curl/yt-dlp/FFmpeg-загрузок из контейнера и
    предложений «скачать напрямую» — только браузерный релей. Риск
    привязки cookies к fingerprint упразднён тем же фактом (качает сам
    браузер со своей сессией/UA/IP) — не «чинить» его.
11. **Чего НЕ делать** (из отчёта §5): vision-first цикл по скриншотам,
    site-адаптеры с реверсом приватных API сайтов (ToS/суды), Set-of-Marks на
    плотных страницах, полный `evalJS` (осознанно исключён из MVP — gated
    backlog, не добавлять без отдельного решения пользователя).
